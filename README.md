# Music Flow · 音乐管家

把「音乐平台歌单 → 本机无损曲库 → 手机」这一整条链路包装成一个**过程透明**的本地应用。

原先是十几个散落的脚本，靠记忆手敲命令调用，出问题只能翻终端历史。现在合成一个界面：日常点一下就走完，出问题时每一步都能单独跑、单独看日志。

> 纯 Python 标准库 + 原生 HTML/CSS/JS，**零第三方依赖**，不需要 pip install、不需要 Node。

## 它解决什么问题

| 问题 | 做法 |
|---|---|
| 每次都要手动敲一串命令 | 双击启动，界面里点一下 |
| 出问题不知道卡在哪一步 | 11 个步骤独立可跑，实时日志 + 运行记录 |
| 低品质文件混进曲库 | 下载策略可配，默认只收无损及以上 |
| 某些音频会损伤听力/设备 | 属性闸门，按采样率、声道拦截 |
| 同名不同格式文件并存 | 落盘时按**实测规格**择优去重，不看扩展名 |
| 标签缺失或写错 | 落盘后按**文件头**判断格式再写标签 |
| 会员歌下下来是加密的，手机放不了 | 落盘前先无损解码（ncm/qmc/kgm/vpr/kgg） |
| 封面歌词要自己一张张找 | 自动补专辑封面 + 带时间轴的歌词 |
| 手机同步永远不知道进度 | 直接读 Syncthing 接口，显示百分比和待传量 |
| 自己下载的歌要手动拷来拷去 | 手动导入单曲/整个文件夹，自动解码、打标签、补封面并进入同步 |

## 两种模式

两种模式**共用同一份流水线定义**（后端 `PIPELINE`），所以"自动跑的"和"手动点的"永远是同一套逻辑，不存在两套实现走偏的问题。

### 省心模式

连上热点后点一下「同步」，11 步自动跑完。适合日常。

### 观察模式

同一个流水线列表，每一步都有独立的「运行」按钮。适合排错：

```
怀疑下载有问题    → 只跑第 ④ 步，看完整输出
下下来是加密文件  → 只跑第 ⑤ 步，看还原成什么格式
怀疑落盘有问题    → 只跑第 ⑥ 步
封面歌词不对      → 只跑第 ⑦ 步（加 --force 会整库重配）
想确认手机连没连  → 只跑第 ⑪ 步
```

## 界面

### 控制台

左侧流水线卡片，每张显示当前状态：

| 颜色 | 含义 |
|---|---|
| 灰 | 待运行 |
| 蓝 | 运行中 |
| 绿 | 完成 |
| 黄 | 待处理（非致命失败，例如手机没连上） |
| 红 | 失败 |

下方实时日志，按级别着色：命令（紫）/ 输出（灰）/ 成功（绿）/ 警告（黄）/ 错误（红粗体）。支持「只看错误」筛选。

### 曲库

用 `ffprobe` **实测**每个文件的真实规格（不看扩展名），显示分布：

```
采样率: 44.1kHz×169  48kHz×63  96kHz×25  192kHz×1  88.2kHz×1
位深  : 24bit×229    16bit×30
声道  : 立体声×259
```

结果有缓存，首次约 90 秒，之后秒开。

### 手动导入

控制台顶部有两个按钮：

```
导入歌曲文件…      选一个或多个音频文件
导入整个文件夹…    选一个文件夹，里面的音频全部导入
```

导入后会走与自动下载**完全相同**的后续流程：

```
选文件 → 识别加密容器并解码 → 探测真实规格 → 安全检查 → 同名去重
       → 拷进同步文件夹 → 打标签 → 补封面歌词 → 触发同步
```

几个要点：

- **用系统原生对话框取路径**。浏览器的 `<input type="file">` 出于安全
  不会给出真实磁盘路径，只能上传副本 —— 而导入需要真实路径。
- **加密音乐先解码再校验**。`.ncm`/`.qmc*`/`.kgm`/`.vpr`/`.kgg` 是加密容器，
  还有酷狗那种**改名成 `.flac` 的**（靠文件头认出来）。不解码的话 ffprobe
  读不出规格，会被当成坏文件丢掉。
- **同名去重按实测规格择优**。目标位置已有同名文件时，比较双方的
  真实规格（是否无损 / 位深 / 采样率），规格高的留下。大小完全相同则直接跳过。
- **同名不同扩展名会先清理**，避免 `X.mp3` 与 `X.flac` 并存。
- **拷贝用临时文件 + 原子改名**，防止同步到半个文件。
- **打标签按文件头魔数判断容器格式**，不信扩展名（见「踩过的坑」）。
- **安全检查照常生效**：命中采样率/声道拦截名单的文件会被拒绝导入。
- **导入完自动补封面歌词**。手动导入的歌和自动下载的歌落到同一个同步
  文件夹，用户看不出区别，所以后续处理必须一样 —— 否则会出现
  「自动下载的有封面、自己导入的没封面」这种两套逻辑。
- 导入是否允许有损由设置里的「导入 · 手动添加歌曲」控制，**默认允许**
  （是你自己挑的文件，通常是有意为之）。

### 设置

| 分组 | 可调项 |
|---|---|
| 下载 | 接受 Hi-Res / 无损 / 有损、目标数量、挑选顺序、最低码率 |
| 拦截 | 拦截采样率、拦截声道数、是否尊重内容错误清单 |
| 封面歌词 | 是否补全、是否也问网易云（中文歌词更全）、单轮上限 |
| 解码 | 是否解码加密音乐、线程数、是否删掉加密原件 |
| 同步 | 同步目录、Syncthing 文件夹 ID、设备 ID、API Key |

枚举项都是下拉框或复选框，不用手打数字。

### 运行逻辑

五个可编辑板块，说明这个应用做了什么、每步原理、依赖哪些开源项目、常见故障排查。内容存在 `logic.json`。

### 拦截清单

被屏蔽的曲目，分两类：**平台无音源**（确实没有无损版本）和**安全检查**（属性会伤害设备）。

### 运行日志

每次运行写一个文件到 `logs/`，按时间倒序列出，点开看完整记录。

## 流水线

| # | 步骤 | 做什么 |
|---|---|---|
| ① | 启动 Docker | 拉起 Docker Desktop，等引擎就绪 |
| ② | 启动容器 | 启动下载引擎与流程宿主容器 |
| ③ | 启动 Syncthing | 拉起同步服务，等 GUI 就绪 |
| ④ | 检查并下载新收藏 | 读歌单 → 与基线比对 → 按音质策略挑曲 → 下载到容器暂存 |
| ⑤ | 解码加密音乐 | ncm/qmc/kgm/vpr/kgg 还原成普通 flac/mp3（无损还原，不是转码） |
| ⑥ | 落盘与整理 | 取暂存 → 属性闸门 → 落盘 → 去重 → 写标签 |
| ⑦ | 封面与歌词 | 给缺封面的补齐专辑图，顺带补歌词 |
| ⑧ | 回写暂存 | 把⑥⑦改过的文件同步回暂存，让下一轮⑥判定「内容未变」而跳过 |
| ⑨ | 安全检查 | 逐文件实测属性，命中拦截名单的删除并屏蔽 |
| ⑩ | 曲库体检 | 检查文件损坏、标签完整、容器与扩展名一致 |
| ⑪ | 同步到手机 | 先判断手机是否在线，再盯同步进度 |

### 第 ⑧ 步（回写暂存）为什么不能省

⑥ 每次运行开头会先拿**上游暂存**镜像覆盖本机暂存（`robocopy /MIR`）。
如果⑦改完曲库就不管了，下一轮⑥读到的还是没封面、没歌词的旧暂存，
判定「内容不同」→ 整份覆盖进曲库 → 封面歌词全被抹掉 → ⑦再联网下载嵌一遍。

实测这个来回的代价：一次 ⑥ 抹掉 **84 个封面、82 份歌词**，
**152 个文件（7.07 GB）**被判「内容不同」；每转一圈都要重传一遍。

所以⑦改完曲库后必须把成果**沿数据流往上游写回**：本机暂存和它的源头
`hires_staging` 都要写。⑧ 用「大小 + 分块 SHA256」判断，内容相同的
一概不碰（mtime 不动），只有真变了的才回写。实测回写后连续两轮都是
**落地 0 个 / 跳过 238 个**，收敛。

> 教训：**修复要打在数据的源头，不是下游。** 只回写本机暂存时，
> 下一轮开头的 `robocopy /MIR` 会把回写成果原样抹掉 —— 看起来像
> 「回写没生效」，其实是打错了地方。

### 停止时为什么有时会先弹一个确认框

有些步骤打断是有代价的（落盘没跑完、暂存只回写了一半……），
点「停止」会先把**这一步的具体影响**摆出来问一次，确认了才停。
启动类步骤（①Docker、②容器、③Syncthing）不弹，点了就停。

顺带修掉的一个更实际的问题：`⑪ 同步到手机` 的进度轮询最多跑 20 分钟，
而这段时间它只是在查 Syncthing 的接口，**没有子进程可杀** —— 靠杀进程生效的
停止逻辑对它完全无效，点了停止要干等到结束。现在两个等待循环里都加了
停止检查，实测响应从「停不下来」变成 **0.3 秒**。

### 第 ⑤ 步（解码）为什么必须排在落盘和封面之前

从网易云/QQ音乐/酷狗客户端下下来的会员歌是**加密容器**：`.ncm`、`.qmc*`、
`.kgm`、`.vpr`、`.kgg`，酷狗还会把加密文件**改名成 `.flac`**。

它们有两个要命的地方：

1. `ffprobe` 读不出采样率/时长 → 下一道属性闸门会把它当成「坏文件」丢掉
2. 手机上的播放器不认这种容器

所以解码必须发生在**打标签和嵌封面之前** —— 加密文件根本没法写元数据。
用 [music-decode](https://github.com/wzy1tenyears/music-decode) 做这件事。

**它不做转码，只解密。** 输出扩展名由解密后的内容魔数决定：里面包的是
flac 就出 `.flac`，包的是 mp3 就出 `.mp3`，音频流逐字节一致。所以不存在
「强制转成 mp3」这回事 —— 那会白白毁掉无损。

安全底线：**产物先用 ffprobe 验一遍，能当音频读才删原件**；读不出就保留
加密原件并报错。故意不看解码器的退出码 —— 它在收尾写标签阶段会踩内存崩掉
（退出码 `0xC0000005`），但音频在那之前已经写完，拿退出码判成败会把每一个
加密文件都误判成失败。

同一段逻辑也接在**手动导入**上：选中的加密音乐先解码再走校验/去重/打标签，
导入完还会自动补封面歌词并跑安全检查 —— 手动导入的歌和自动下载的歌待遇一致。

### 第 ⑥ 步（落盘与整理）为什么曾经最慢（已优化掉）

它要把容器暂存里的全部音频（约 11.5 GB）搬到宿主机。原先用 `docker cp`，
实测只有约 **92 MB/s** —— 因为数据要穿过 Docker 的虚拟机代理。

**但这段路是白绕的。** `docker inspect` 显示容器里的 `/app/data`
其实是宿主机目录的 bind 挂载：

```
bind   D:/music-monitor/config/monitor  ->  /app/data
```

也就是说「容器暂存」本来就躺在宿主机磁盘上，根本不需要经过 docker 搬运。

实测（160 MB 单个文件）：

| 方式 | 速度 |
|---|---|
| 直接文件拷贝 | 1548 MB/s |
| `docker cp` | 92 MB/s（慢 16.7 倍） |

改用 `robocopy /MIR` 直连宿主机目录，而且它是**增量**的
（比对时间戳 + 大小，只搬变化的文件）：

```
第 ⑥ 步总耗时:   221 秒  ->  11 秒   (20 倍)
其中「取暂存」:  202 秒  ->   0 秒
```

优化后的耗时分布：

| 子阶段 | 耗时 |
|---|---|
| 阶段 2 取暂存 | 0 秒 |
| 阶段 2.5 采样率闸门 | 2 秒 |
| 阶段 3 落盘 + 精简 | 6 秒 |
| 阶段 5 写标签 | 3 秒 |
| **合计** | **约 11 秒** |

> 教训：**看到「跨容器拷贝」先确认是不是 bind 挂载。**
> 如果是，走 docker 就是在绕远路 —— 数据本来就在本机磁盘上。
### 第 ⑪ 步为什么是「非致命」

前面的工作（曲库更新、标签修正、封面歌词）在第 ⑤-⑩ 步就已经落地了。手机没连上不代表这些白做，所以这一步失败只标黄，不让整次运行显示为失败。

## 安全机制

### 为什么要做属性闸门

实测发现：**176.4 kHz 采样率的文件在「手机 + USB DAC」链路上会输出极大噪声**，必须拔耳机才能停止。同一套设备播放 192 kHz / 96 kHz / 44.1 kHz 全部正常。

已排除：块大小、响度、峰值、DC 偏移、数字尖刺。确认是该采样率档位的问题。

因此 `176400` 进入拦截名单 —— 不下载、不放行、并永久屏蔽。

### 三道防线

1. **属性闸门** —— 拦截会伤害设备的属性（采样率、声道数，可配置）
2. **屏蔽名单** —— 平台无音源的曲目不再反复重试；内容错误的曲目不再重复下载
3. **不降级** —— 拿不到无损以上就跳过，绝不用有损文件顶替（除非明确允许）

### 数据一致性

- 落盘时先删同名异扩展名文件，避免 `X.mp3` 与 `X.flac` 并存
- 去重按 `ffprobe` 实测规格择优，**不看扩展名**（平台返回的扩展名不可信）
- 写标签按**文件头魔数**判断真实容器格式（大量文件是「伪装成 .mp3 的 FLAC」）
- 写标签必须在落盘**之后**，否则会被暂存副本覆盖

## 快速开始

### 环境要求

| 组件 | 用途 |
|---|---|
| Python 3.10+ | 后端（只用标准库） |
| Docker Desktop | 下载引擎运行环境 |
| Syncthing | 文件同步 |
| FFmpeg / ffprobe | 探测音频真实规格 |
| PowerShell 5.1+ | 调用落盘脚本 |

### 步骤

```bash
# 1. 克隆
git clone https://github.com/GUSHAxvx/music-flow.git
cd music-flow

# 2. 生成配置
cp config.example.json config.json
# 然后编辑 config.json，填入你自己的路径和 Syncthing 信息

# 3. 启动
python music_flow.py
```

会自动打开浏览器到 `http://127.0.0.1:8477/`。

Windows 下也可以直接双击：

```
启动音乐管家.bat
```

想要桌面图标（带自定义图标，双击即启动）：

```bash
python scripts/setup_shortcut.py
```

会在桌面创建 `Music Flow.lnk`，指向项目里的启动器。
图标是项目自带的 `assets/music-flow.ico`（可在 `scripts/make_icon.py`
里改配色后重新生成）。

### Syncthing 信息怎么填

在 Syncthing GUI（默认 `http://127.0.0.1:8384`）里：

| 字段 | 在哪看 |
|---|---|
| `api_key` | 操作 → 设置 → API 密钥 |
| `phone_device` | 右侧设备列表点开手机，看「设备 ID」 |
| `folder_id` | 文件夹列表里，点开同步文件夹看「文件夹 ID」 |

## 配置说明

`config.json` 已加入 `.gitignore`，**不会**被提交。仓库里只有 `config.example.json` 模板。

### download

| 键 | 说明 |
|---|---|
| `accept_hires` | 接受 24bit Hi-Res |
| `accept_lossless` | 接受 16bit 无损（CD 规格） |
| `accept_lossy` | 接受有损（128k/320k）。想补只有有损版本的歌时才开 |
| `only_new_lossless` | **无损只跟新歌**（默认开）。只下载基线之后新增的、且只有无损版本的歌，不回填历史。打开时 `lossless_target` 被完全忽略 |
| `lossless_target` | 仅在 `only_new_lossless` 关闭时生效：回填多少首历史无损 |
| `max_albums` | 首次回填规模。**曲库建立基线后此值不生效**（代码里被主动绕过） |
| `sort_mode` | `bitrate` 优先高码率 / `newest` 优先最新收藏 |
| `min_bitrate` | 最低码率，0 = 不限 |

### guard

| 键 | 说明 |
|---|---|
| `block_sample_rates` | 要拦截的采样率列表 |
| `block_channels` | 要拦截的声道数列表，留空 = 不拦 |
| `content_mismatch_blocklist` | 是否尊重内容错误清单 |

### import

| 键 | 说明 |
|---|---|
| `accept_lossy` | 手动导入时是否接受有损文件。默认 `true` |

### sync / docker / advanced

路径与连接信息。`advanced` 里是外部脚本位置，一般不用改。

```
logs/                    运行日志（不入库）
```

> 解码器本身不在这个仓库里，是单独构建的
> [music-decode](https://github.com/wzy1tenyears/music-decode)：
> `D:\music-decode\build\music_decode.exe`（构建脚本 `D:\build-dep\build_decode.bat`，
> 依赖 TagLib，TagLib 由 `D:\build-dep\build_taglib.bat` 单独编好）。

### 关键设计

**流水线只有一份定义**

```python
PIPELINE = [
    {"id": "docker", "name": "① 启动 Docker", "fn": s_docker_start},
    ...
    {"id": "sync", "name": "⑩ 同步到手机", "fn": s_sync, "soft": True},
]
```

自动模式遍历它，观察模式从它里面挑一个。前端不硬编码步骤，由 `/api/pipeline` 下发，保证前后端一致。

**实时日志走 SSE**

后端有个事件总线，日志一产生就推给所有连接的前端。不用轮询，也不丢行。

**长任务可中断**

```python
subprocess.run(["taskkill", "/T", "/F", "/PID", str(pid)])
```

必须杀**整棵进程树** —— 只杀父进程的话，它派生的 `docker cp`、`ffprobe` 还在继续跑（实测停止后仍等了 80 秒；改成杀树后是 5 秒）。

**日志双写**

`log()` 既推前端也写文件。只推前端的话，出问题后翻运行日志会看不到任何线索。

## 踩过的坑

这些是实际调试中撞到的，记录在此避免重犯。

### 1. `subprocess` 不过 shell，参数里别带引号

```python
# ❌ 引号会被当成参数内容，程序去创建名为 `"C:` 的目录
'--config="C:\\ProgramData\\Syncthing\\config"'

# ✅
r"--config=C:\ProgramData\Syncthing\config"
```

### 2. 杀进程要杀整棵树

`p.kill()` 只杀父进程，子进程继续跑。Windows 上用 `taskkill /T /F`。

### 3. 缓存字段新增后，旧缓存会让新检查静默失效

给探测加了声道数之后，旧缓存里没有这个字段，程序读不到就跳过判断，最后报「✅ 没有需要拦截」—— **安全检查假装通过了**。

修法：缓存条目缺必需字段时强制重新探测，不依赖用户手动清缓存。

> 这类 bug 最危险：不报错，只让你以为安全。

### 4. 日志误报

`补写完成: 成功 67, 失败 0` 含「失败」二字，被错误检测标红。需要豁免规则：

```python
ERROR_EXEMPT = (r"成功\s*\d+\s*[,，]\s*失败\s*0", ...)
```

### 5. 目标数量传错会误触发安全中止

落盘脚本有个保护：实际数量比目标少 15 个以上就中止（防下载残缺）。如果传的目标远大于实际，它会误判成「下载未完成」。

修法：每次运行前先数暂存实际数量，用它当目标。

### 6. PowerShell 里给 `docker exec -e` 传 JSON 会丢引号

```powershell
# ❌ 引号被吃掉，容器里收到 {accept_hires:true,...} 解析失败
docker exec -e 'DOWNLOAD_POLICY={"accept_hires":true}' ...

# ✅ 用 Python subprocess 传列表参数
subprocess.run([docker, "exec", "-e", 'DOWNLOAD_POLICY={"accept_hires":true}', ...])
```

### 7. 音频扩展名不可信

平台返回的 `extname` 可能是 `mp3`，实际内容是 24bit FLAC。**读写标签都必须按文件头魔数判断格式**。

反过来，如果按扩展名写 ID3 到 FLAC 文件上，会在文件开头插入 `ID3\x04` 头，**破坏文件**。

### 8. 「移出计划」被当成「该删除」——误删了 27 首歌

无损严格模式会把历史无损移出计划。而落盘脚本原本的逻辑是
「凡是不在保留集里的文件一律删除」，于是把这些**用户已经拥有**的歌清掉了
（实测从 264 首掉到 237 首）。

修法：落盘脚本只删除**屏蔽名单里明确拦截的**文件，其余一律保留：

    $toDelete = @($notKept | Where-Object { $blockedSet.ContainsKey(...) })

教训：**自动删除必须要有明确白名单依据**，不能靠「不在计划里」这种
间接推断 —— 计划会因为各种配置变化而收缩。

### 9. .bat 必须 ANSI/GBK + CRLF

UTF-8 编码的 `.bat` 里带中文，cmd 会按当前代码页解析成乱码命令，
报 `'xx' 不是内部或外部命令`。纯 LF 换行在部分 Windows 上也会解析异常。
生成脚本里已经写死成 `gbk` + `\r\n`（见 `scripts/setup_shortcut.py`）。

### 10. 有些 mp3 的 ffprobe 输出带尾逗号

```
"44100,"   # 直接 int() 会炸
```

需要按段切分取值。

### 11. 含中文的 `.ps1` 必须存成 UTF-8 **带 BOM**（否则导入按钮点了没反应）

Windows PowerShell 5.1 读 `.ps1` 的规则是「有 BOM 按 BOM，**没 BOM 按系统 ANSI(CP936)**」。
纯 ASCII 的脚本无所谓，但只要里面有中文字符串，丢了 BOM 就会连锁崩：

```
中文按 GBK 解读成乱码字节 → 某些字节恰好是 0x27(单引号) → 引号提前闭合
→ 解析器报「字符串缺少终止符」→ 整个脚本解析失败，run 都不 run
```

最坑的是它**静默失败**：脚本 exit 0 且没有任何输出。2026-10-15 那次
`pick_files.ps1` 丢了 BOM，用户点「导入歌曲」什么都不弹，
日志里只有一句「未选择任何内容（或对话框被取消）」，极难定位。

所以：**编辑这类脚本时用会保留 BOM 的方式写回**（很多工具/编辑器默认吃掉它），
改完跑一次自检：

```bash
python scripts/check_ps1_encoding.py         # 只检查，有问题 exit 1
python scripts/check_ps1_encoding.py --fix   # 顺手补回 BOM
```

它的规则就两条：含非 ASCII 的 `.ps1` 必须有 BOM；没有 BOM 的必须纯 ASCII。
`scripts/pixel_stats.ps1` 是故意保持纯 ASCII 的（所以它免检）。

同理，PowerShell 5.1 往管道写字符串用的是**控制台输出编码（中文系统上是 GBK）**，
不是 UTF-8。`pick_files.ps1` 现在已经显式钉死
`[Console]::OutputEncoding = New-Object System.Text.UTF8Encoding $false`，
Python 侧的 `import_songs._decode_console_bytes()` 也做了「UTF-8 坏了就回退 GBK」的兜底，
两边任意一边单独坏掉都不会再丢字符。
